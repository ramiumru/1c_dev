# Specs — SDD-спецификации задач (Spec-Driven Development)

Каталог для полноценных SDD-спецификаций задач по правке конфигурации 1С.
Каждая задача живёт в отдельной папке `specs/<TASK-ID>/`.

> Для не-SDD задач (быстрые наброски требований, уточнения по существующим
> объектам без полноценной spec) используется каталог `{{CONTEXT_DIR}}/projects/<проект>/requirements/**`.
> SDD-режим запускается только для **нетривиальных правок кода** (новая бизнес-логика,
> правка проведения, изменение форм, риск регрессии). Решение о нетривиальности —
> на `1c-do`; при сомнении запускать SDD. Тривиальные правки (опечатка, комментарий)
> и чистый анализ идут без SDD.

## TASK-ID

- Если пользователь дал GitLab-номер задачи (`#481`) — `TASK-481`.
- Если GitLab-номера нет — `1c-do` генерирует `TASK-YYYYMMDD-HHMMSS` по `Current time`
  системного контекста.

Этот же TASK-ID используется в комментариях BSL:
`// ++ #<TASK-ID>` … `// -- #<TASK-ID>` (согласуется с
`{{CONTEXT_DIR}}/standards/standards.example.md`, раздел «Комментарии изменений»).

## Распределение прав на `specs/**`

| Агент | Что пишет |
|---|---|
| `1c-do` | каркас task-папки + `00_request.md` (только эти файлы) |
| `1c-analyst` | `01_context.md`, `03_solution_spec.md` (вкл. машиночитаемый блок status/risk), `05_test_scenarios.md` |
| `1c-developer` | `06_change_report.md` (после реализации; + `scope_hash` для сверки) |
| `1c-reviewer` | `review.md` (независимое заключение: verdict + findings) |
| `1c-applier` | ничего не пишет в `specs/**` и `pilot-control/**`; читает `06_change_report.md` + `pilot-control/<TASK-ID>/review.md` + блок status/risk |

`1c-do` также проверяет gate перед вызовом `1c-developer`: наличие
`03_solution_spec.md` в `specs/<TASK-ID>/` **и машиночитаемого блока `status: approved`**
(см. «Risk gates»). Если отсутствует, пуст или `status ≠ approved` — возвращает
задачу `1c-analyst`.

### Risk gates (машиночитаемый блок)

Само наличие файла спецификации не разрешает разработку или применение. В
`03_solution_spec.md` обязателен блок (fenced `yaml`):

```yaml
status: draft | ready_for_review | approved | rejected
risk: low | medium | high
approved_by: null
approved_at: null
spec_version: 1
scope_hash: null
```

Правила:
- документ без блока статуса считается неподтверждённым;
- `draft` не допускается в разработку; `ready_for_review` ожидает проверки;
  `rejected` блокирует работу; `approved` разрешает следующий этап с учётом риска;
- `approved` требует непустые `approved_by` и `approved_at`;
- `approved_by` не может быть `1c-developer` (само-подтверждение запрещено);
  для `risk: high` — также не может быть `1c-analyst`;
- review (`review.md` с `verdict: approved`) обязателен **для всех** опасных операций apply,
  не только для `risk: high`; для `risk: high` дополнительно требуется независимость:
  `reviewed_by` ≠ `approved_by`;
- `scope_hash` обязателен (непустой) в spec, `06_change_report.md` и `review.md`; все три
  должны совпадать (выход за scope блокируется);
- `spec_version` в spec и review должны совпадать;
- изменение спецификации или scope аннулирует подтверждение (`status` → `draft`,
  `approved_by`/`approved_at`/`scope_hash` → `null`);
- `1c-developer` не начинает неподтверждённую реализацию;
- `1c-applier` не применяет изменения без нужного статуса и review — проверяет
  `scripts/applier_guard.py`; опасные операции выполняются **только через**
  `scripts/safe_apply.py` (wrapper, принудительно запускающий guard, затем skill);
  прямой вызов `db-load-*`/`db-update` skills запрещён правами (frontmatter);
- `environment` задаётся **per-db** в записи базы (не глобально); для серверных баз
  дополнительно требуется `allow_apply: true`; глобальный `environment` — только
  fallback для файловых баз.

К высокому риску относятся: проведение документов; движения регистров; транзакции и
блокировки; RLS и права; фоновые и регламентные задания; публичные экспортные процедуры;
изменение метаданных; интеграционные контракты; изменение структуры базы; массовое
изменение данных; обмены; финансовые расчёты.

Файлы `specs/README.md` и структура каталога правятся только пользователем вручную
вне сессии агента (см. `INSTRUCTIONS.md`, раздел «Правка конфигурации агентов»).

## Набор артефактов MVP (5 файлов)

```
specs/
└── <TASK-ID>/
    ├── 00_request.md           — исходный запрос (1c-do)
    ├── 01_context.md            — контекст системы и объектов (1c-analyst)
    ├── 03_solution_spec.md      — спецификация решения + машиночитаемый блок status/risk, GATE для 1c-developer (1c-analyst)
    ├── 05_test_scenarios.md     — сценарии тестирования (1c-analyst)
    ├── 06_change_report.md      — отчёт об изменениях + scope_hash (1c-developer)
    └── review.md                — независимое заключение 1c-reviewer (verdict + findings)
```

### 03_solution_spec.md

> Главный документ. Это договор между аналитиком и разработчиком.
> **GATE для `1c-developer`**: без этого файла (или при пустом/неполном) —
> разработчик не начинает реализацию.

```markdown
# Solution Spec: <TASK-ID>

<!-- Машиночитаемый блок статуса и риска (risk gate). НЕ удалять. -->
```yaml

risk: low
approved_by: null
approved_at: null
spec_version: 1
scope_hash: null
```

> `status` переводит аналитик/user: `draft` → `ready_for_review` → `approved`/`rejected`.
> `approved` (с `approved_by`/`approved_at`) разрешает разработку. Для `risk: high`
> требуется verdict `1c-reviewer` в `review.md`. `scope_hash` = sha256 от
> канонизированных «Границ изменения» + «Затрагиваемые файлы» (заполняется/сверяется
> при review и apply).

## Цель изменения
<что и зачем меняется>

## Roadmap расширения (НЕ входит в MVP)

Перечисленные ниже элементы заложены как точки расширения. Реализуются по мере
необходимости; до этого момента MVP работает без них.

- **`meta.json` + state machine** — машиночитаемый статус задачи. Состояния:
  `NEW → TRIAGE → CONTEXT_COLLECTED → ANALYSIS_IN_PROGRESS → SPEC_DRAFTED →
  SPEC_REVIEW → APPROVED_FOR_IMPLEMENTATION → IMPLEMENTATION_IN_PROGRESS →
  IMPLEMENTED → SELF_CHECK → READY_FOR_QA → DONE / REJECTED`.
- **Дополнительные артефакты:**
  - `02_analysis.md` — отдельный аналитический документ (сейчас объединён с
    `01_context.md`);
  - `04_implementation_plan.md` — пошаговый план реализации;
  - `07_open_questions.md` — недоопределённые кейсы;
  - `traceability.md` — связь «требование → файл → процедура → статус»;
  - `glossary.md` — глоссарий предметной области;
  - `architecture_notes.md` — повторяющиеся проектные решения.
- **Дополнительные gate'ы** из полного SDD-документа:
  - Gate 1 — допуск к анализу (понятен ли бизнес-запрос);
  - Gate 3 — завершение разработки (соответствие spec, нет скрытых доработок);
  - Gate 4 — готовность к QA (`05_test_scenarios.md` + `06_change_report.md`).
  В MVP реализован только Gate 2 — допуск к разработке (наличие
  `03_solution_spec.md`).
- **Git workflow** (когда в окружении появится git):
  - нейминг веток: `feature/TASK-ID-short-name`, `bugfix/...`, `refactor/...`;
  - семантика коммитов: `chore(TASK-ID): ...`, `docs(TASK-ID): ...`,
    `feat(TASK-ID): ...`, `fix(TASK-ID): ...`, `refactor(TASK-ID): ...`;
  - PR template (с чек-листом артефактов SDD);
  - CI-проверка «нет `.bsl`/`.xml` без `specs/<TASK-ID>/`»;
  - `pre-commit`/`commit-msg`/`pre-push` hooks.
- **Интеграция с BSL Language Server** (см. `AGENTS.md`, раздел «Опциональный автолинт
  через BSL Language Server») — запуск автолинта в рамках Gate 3 / SELF_CHECK.
- **Ужесточение прав на `specs/**`** — в MVP все три агента (`1c-do`, `1c-analyst`,
  `1c-developer`) имеют физическое `edit: "specs/**": allow`, ограниченное только
  поведенческими правилами промпта (каждый пишет только свои артефакты). Это
  defense-in-depthgap: при сбое модели агент может записать чужой артефакт. Когда
  движок прав Kilo поддержит файл-нейм-паттерны — сузить `edit` до конкретных файлов:
  - `1c-do` — `specs/<TASK-ID>/00_request.md` (каркас);
  - `1c-analyst` — `specs/<TASK-ID>/{01_context,03_solution_spec,05_test_scenarios}.md`;
  - `1c-developer` — `specs/<TASK-ID>/06_change_report.md`.
- **Интроспекция SDD-задач** — запрос «покажи активные SDD-задачи» (пока нет
  `meta.json`, реализуется через glob по `specs/` с проверкой наличия
  `06_change_report.md`).
