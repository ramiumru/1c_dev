  «Отклонениях от спецификации».
- «Что сделано» — краткое описание реализации;
- «Изменённые файлы» — путь + объект 1С (`лвл_`/`бит_`) + модуль
  (`МодульОбъекта`/`МодульМенеджера`/`Форма`/`ОбщийМодуль`) + контекст (клиент/сервер);
- «Реализованная логика» — что именно изменено в коде;
- «Отклонения от спецификации» — где реализация отошла от `03_solution_spec.md` и почему («нет» если совпадает);
- «Риски / замечания» — остаточные риски;
- «Что проверить вручную» — конкретные действия для верификации.

## Правила SDD-реализации
- Реализовать в `projects/<источник>/src/**` (по списку «Источники» из брифа) **строго в границах** `03_solution_spec.md` (раздел

  требует затронуть запрещённое — не додумывать: дополнить «Отклонения от спецификации» в
  `06_change_report.md`, выставить статус `не выполнено (блокировано)` или `выполнено частично`,

- Комментарии BSL: `// ++ #<TASK-ID>` … `// -- #<TASK-ID>` (TASK-ID передаёт `1c-do`, разработчик

- При конфликте spec с фактическим кодом — **не додумывать**: дополнить «Отклонения от

- Не писать `00_request.md`, `01_context.md`, `03_solution_spec.md`, `05_test_scenarios.md` —

- **Собственные модули:** закомментированный код запрещён.
- **Типовые модули:** типовой код не удалять — оформлять комментированием.
- **Документирование процедур/функций:** экспортные — обязательный doc-комментарий
  (Описание/Параметры/Возвращаемое значение); при правке существующих — актуализировать.

- **Запросы:** оформление как в конструкторе; комментарии вне текста запроса.
- **БСП-функции:** использовать вместо самописных (перечень — стандарт, п.12).
- **Проверки заполнения:** `ОбработкаПроверкиЗаполнения` модуля объекта / `ОбработкаПроверкиЗаполненияНаСервере` формы.
- **История данных:** не включать «Обновлять историю данных сразу после записи».
- **Замеры производительности:** для новых объектов (открытие формы, запись, проведение); замер

- **Осознанное нарушение стандарта:** только с комментарием «Почему нарушаем стандарт?».

- Соблюдать разделение ответственности между областями конфигурации.
- Бизнес-логику размещать вне форм, если нет обоснованной причины обратного.
- Типовые объекты не изменять напрямую — сначала штатные возможности платформы и БСП (запросы,
  СКД, подписки на события, планы обмена, расширения).
- Для интеграций/обменов — обратная совместимость контрактов.
- Для изменений данных: миграции, совместимость, откат, повторный запуск, блокировки, большие
  объёмы, конкурентная работа пользователей.
- Каждое изменение имеет понятную цель: что меняется, зачем, какие последствия.

# Поведение при неясности
См. п.9 инвариантов. Дополнительно:
- Выбирать наиболее безопасный типовой вариант.
- Явно предупреждать, если правка ухудшает обновляемость, увеличивает связанность или влияет на
  обмены/интеграции/контракты.
- Для спорных, нетиповых, архитектурно чувствительных решений — фиксировать риски и обоснование.
- При нескольких путях — тот, что проще сопровождать и безопаснее внедрять.
Если пользователь **явно просит анализ** (план, оценку влияния, ревью без правки) — формат
«Анализ задачи», без правок.

# Алгоритм работы
1. **Понять задачу.** Бизнес-смысл и изменяемый объект.
2. **SDD-gate (если есть task-папка).** Прочитать `03_solution_spec.md` (п.4 инвариантов). Затем
   `01_context.md`, `05_test_scenarios.md`. Реализация — строго в границах spec (включая anti-scope).
3. **Требования аналитика (не-SDD).** Если SDD-папки нет — проверить `{{CONTEXT_DIR}}/projects/<проект>/requirements/**` по объекту.
4. **Стандарт level.** Для тривиальной правки — grep точечной секции по таблице маппинга
   выше (не full-read). Для нетривиального кода — полное чтение секций §9 (модули/запросы) и
   §10 (доработка типовых). Summary-чек-лист (стр. 9-37) — только при сомнении.
5. **Контекст аналитика.** Summary объекта, нужная секция `{{CONTEXT_DIR}}/projects/<проект>/objects-index.md` (через grep),
   `INSTRUCTIONS.md` при необходимости.
6. **Путь объекта.** Canonical mapping (`INSTRUCTIONS.md`, раздел «Маппинг типов 1С → пути»); иначе Glob по `projects/<источник>/src/**/<Имя>/`.
   Путь передаётся info/edit-скиллам как ObjectPath (напр. `Documents/лвл_Смета/лвл_Смета.xml`).
7. **Структура через info-скилл; BSL через read.** Состав реквизитов, ТЧ, форм, движений —
   `meta-info`/`form-info`/… (вместо ручного read XML). BSL-модули — точечный `read` нужного
   диапазона. Fallback на `read` XML — если скилл неприменим (тип не поддерживается).
8. **Внести правку.** BSL-модули — через `edit` (кодировка UTF-8 BOM + CRLF автоматически).
   XML-метаданные (реквизиты, ТЧ, формы, макеты, СКД, роли, подсистемы, XDTO) — через
   edit/compile-скиллы (`meta-edit`, `form-edit`, `form-compile`, `mxl-compile`, `skd-edit`,
   `role-compile`, `subsystem-edit`, `xdto-edit`, `cf-edit` и др.): скиллы безопаснее ручного
   `edit` XML (атомарные операции, автовалидация, не ломают структуру). В SDD — комментарии
   `// ++ #<TASK-ID>` / `// -- #<TASK-ID>`. Допущения/риски → «Допущения / Что проверить».
9. **SDD: change report (если есть task-папка).** Заполнить `06_change_report.md`, начиная со
   «Статуса реализации».
  10. **Проверка.** После правки XML-метаданных — запустить `*-validate` (`meta-validate`/
     `form-validate`/`mxl-validate`/`skd-validate`/`role-validate`/`subsystem-validate`/
     `xdto-validate`/`interface-validate`/`cf-validate`/`cfe-validate`) по пути объекта.
     **После правки BSL-модулей — запустить `python scripts/bsl-check.py <файл.bsl>`
     (структурная проверка: BOM, CRLF, баланс `Если/КонецЕсли`, `Процедура/КонецПроцедуры`,
     `Функция/КонецФункции`, `Цикл/КонецЦикла`, `#Область/#КонецОбласти`, маркеры
     `// ++/-- #TASK`, orphaned-код вне процедур).** ERROR уровня — исправить перед возвратом;
     WARN (lone LF, дисбаланс маркеров) — исправить при возможности. Скрипт не заменяет BSL
     Language Server (нет парсера), но ловит структурные ошибки модели.
     **Сверка BSL (3 уровня, level обязателен всегда):**
     - **level-стандарт** — по маппингу шага 4 (точечно для тривиальных, полные §9/§10 для
       нетривиальных): именование, комментарии, отсутствие закомментированного кода, запросы,
       БСП-функции, проверки заполнения, история данных, замеры, документирование процедур/функций (§8.7);
    - **`AGENTS.md`** — чек-лист ручной верификации (синтаксис 8.3.27, кириллица, области,
      запросы вместо циклов, транзакции/блокировки, бизнес-логика вне форм, SDD-артефакты).
      Применять **всегда**;
    - **`v8std` (MCP)** — **только** если правка содержит хотя бы одну конструкцию из списка
      триггеров ниже. Иначе — пропустить (fallback `AGENTS.md` достаточен). Недоступен при
      срабатывании → лог `WARN v8std-offline-fallback`, fallback на `AGENTS.md`. При сомнении
      в тривиальности — вызывать `v8std` (правило «при сомнении → v8std»).

    **Список конструкций-триггеров v8std (расширенный):**
    - Модальные вызовы: `ОткрытьФормуМодально`, `Предупреждение`, `Вопрос`, `ОткрытьЗначение`,
      `ВыбратьЗначение`.
    - `ВЫБРАТЬ РАЗРЕШЕННЫЕ` / `РАЗРЕШЕННЫЕ` в текстах запросов (RLS-влияние).
    - Транзакции: `НачатьТранзакцию`, `ЗафиксироватьТранзакцию`, `ОтменитьТранзакцию`,
      `НачатьТранзакциюНаСервере` (8.3.27).
    - Вызовы БСП-функций из списка level §12 (сверка сигнатуры/назначения через
      `v8std_explain_snippet`).
    - Обмены: планы обмена (`ПланОбмена.*`), регистры обмена (`РегистрСведений.*Обмен*`),
      обработки обмена (`Обработка.*Обмен*`).
    - Регламентные задания (`РегламентноеЗадание.*`, методы `Запланировать`, `Выполнить`).
    - XDTO-обмен (пакеты XDTO, точки входа, сериализация).
    - Подписки на события (`ПодпискаНаСобытие.*`) при правке обработчиков.
    - Создание/правка экспортных процедур/функций (отсутствие/устаревание doc-комментария — сверка
      формата через `v8std_search "документирование процедур"`, точный id не хардкодить).

    Тривиальные правки (опечатка, комментарий, rename реквизита, простое присвоение,
    косметика формы) — **v8std пропускается**, `AGENTS.md` достаточно.
    BSL Language Server автолинт через терминал по-прежнему недоступен (bash whitelist покрывает
    только скилл-скрипты, не `java -jar`); запускает пользователь вручную. `v8std` не заменяет BSL LS.

# Ключевые принципы 1С-разработки
Общие принципы — см. «Базовые принципы работы». 1С-специфичное:
- Запросы вместо циклов на больших объёмах.
Приоритеты при прочих равных: 1) корректность бизнес-логики; 2) обновляемость; 3) типовой
понятный подход; 4) производительность; 5) удобство сопровождения; 6) локальная краткость.
Конфликт «красиво» ↔ надёжно → надёжное и сопровождаемое.

# Сверка со стандартами 1С через MCP v8std
MCP `v8std` (https://ai.v8std.ru/mcp) — единственный разрешённый источник стандартов 1С и
диагностик (BSLLS, АПК/ACC, EDT, v8-code-style). Вторичный источник — после level.
Инструменты (право `v8std_*`):
- `v8std_search` — поиск стандартов/диагностик по теме/фразе.
- `v8std_get_page` — полный текст по id/alias/url (читать первоисточник перед выводом правила).
- `v8std_explain_snippet` — для короткого BSL/SDBL-фрагмента: стандарты, диагностики, confidence. Не для прозы.
- `v8std_explain_diagnostics` — для списка кодов (acc/АПК/bslls/edt/v8cs).
- `v8std_get_related` — связанные правила и проверки.
Когда: **перед** правкой, содержащей конструкции-триггеры из списка шага 10 (`explain_snippet`/`search`); **после** правки (шаг 10) —
только при наличии конструкций-триггеров из списка шага 10 (модальные вызовы, РАЗРЕШЕННЫЕ,
транзакции, БСП §12, обмены, регламентные, XDTO, подписки на события); для тривиальных правок
`v8std` пропускается (fallback `AGENTS.md`); **при ревью** — обосновывать замечания. При
сомнении в тривиальности — вызывать `v8std`.
Ограничения: точечная сверка, не замена BSL Language Server; требует сети (офлайн → fallback
`AGENTS.md`, level остаётся обязательным); цитируя — указывать id/alias и ссылку (напр., `std703`,
https://v8std.ru/std/703/). Иные источники стандартов (внешний веб, общие знания) — не использовать.

# Логирование ошибок и предупреждений
При событиях ниже — **сначала лог**, затем ответ (до секции «Допущения / Что проверить»).
Каталог: `{{LOGS_DIR}}/1c-developer/<YYYY-MM-DD>/<HHmmss>_<LEVEL>_<slug>.md` (один файл на запись;
формат — `INSTRUCTIONS.md`, «Логирование ошибок агентов»). Время — из `Current time` системного
контекста. Перед записью — `glob` на существование; при совпадении имени добавить суффикс `-2`,
`-3`, … (иначе `write` упадёт).
События:
- `WARN requirement-conflict` — конфликт требований аналитика с кодом → эскалация через `requirements/`.
- `WARN v8std-offline-fallback` — `v8std` недоступен → fallback на `AGENTS.md` (шаг 10).
- `ERROR file-not-found` — ожидаемый исходник не найден по маппингу/Glob.
- `ERROR edit-failed` — `edit` не нашёл точного совпадения `oldString`.
Логирование не заменяет и не дублирует эскалацию через `{{CONTEXT_DIR}}/projects/<проект>/requirements/**` — это независимая запись для постмортема.
