# Стандарты разработки level для BSL-кода

Корпоративные стандарты разработки компании level для конфигурации БИТ.ФИНАНС / БИТ:Строительство КОРП 3.0. Применяются при написании и ревью BSL-кода как **первичные** — выше стандартов 1С из MCP `v8std`.

Правит файл только пользователь вручную вне сессии агента.

---

## Summary (краткий чек-лист)

1. Код с нарушениями стандартов или замечаниями SonarQube не считается готовым к рабочему окружению.
2. Осознанное нарушение стандарта — только с комментарием, объясняющим, **почему нарушаем стандарт**.
3. Минимизировать изменения типового кода: типовые формы — программно, типовые макеты — через копию, типовые запросы — через переопределение текста/объекта запроса, а не прямую правку.
4. Соблюдать соглашения по именованию:
   - новые реквизиты/ТЧ в типовых объектах — с префиксом `лвл_`;
   - новые объекты конфигурации — с префиксом `лвл_`, но подчинённые элементы нового объекта — без префикса;
   - у новых объектов и элементов в комментарии обязательно указывать назначение.
5. Формат комментариев изменений в коде: `// ++ #НомерЗадачиGitLab` … `// -- #НомерЗадачиGitLab`. Без фамилий, дат, emoji и произвольных форматов.
6. В типовых модулях запрещено удалять типовой код — изменения оформляются через комментирование/обрамление по стандарту.
7. В модулях собственной разработки запрещено оставлять закомментированный код.
8. Тексты запросов не комментировать внутри текста запроса; при необходимости комментарий оставлять рядом с объектом `Запрос`.
9. Оформление кода:
   - делить код на логические блоки;
   - не использовать двойные пробелы и лишние переносы строк;
   - ключевые слова отделять пробелами;
   - пустые области (без процедур/функций) удалять;
   - порядок обработчиков формы/модуля соответствует порядку в Конфигураторе;
   - тексты запросов оформлять как в конструкторе запросов.
10. Предпочитать стандартные функции БСП и 1С вместо самописных решений, если они решают задачу.
11. Проверки заполнения реквизитов размещать в правильных точках:
    - объекта — в `ОбработкаПроверкиЗаполнения`;
    - формы — в `ОбработкаПроверкиЗаполненияНаСервере` для данных формы.
12. Нельзя включать свойство «Обновлять историю данных сразу после записи» у объектов с историей данных.
13. Для новых объектов нужны замеры производительности: открытие формы, запись, проведение. Замер пользовательского процесса начинать и завершать на клиенте.
14. Экспортные процедуры/функции — с doc-комментарием (Описание/Параметры/Возвращаемое значение); при правке существующих — актуализировать (см. §8.7).

## 1. Обязательность соблюдения стандартов

- Все разработчики обязаны соблюдать стандарты разработки компании.
- Нарушения, найденные SonarQube, обязательны к исправлению.
- Код с нарушениями стандартов не должен считаться готовым к поставке, кроме отдельно оговорённых исключений.

### Практическое правило для AI-агента

При генерации кода исходить из того, что:

- код должен проходить ревью по стандартам;
- нельзя предлагать решения, которые заведомо конфликтуют с SonarQube или локальными соглашениями.

---

## 2. Экранирование / осознанное нарушение стандарта

Если правило невозможно применить, стандарт допускает экранирование, **но обязательно с комментарием**, объясняющим причину.

### Обязательное правило

При любом осознанном отступлении от стандарта добавлять пояснение, отвечающее на вопрос:

- **Почему нарушаем стандарт?**

---

## 3. Договорённости по запросам

### 3.1. Пакетное выполнение запросов

`Запрос.ВыполнитьПакет()` использовать осмысленно:

- **плюс:** меньше нагрузка на СУБД, одна сессия, консистентность данных между запросами;
- **минус:** сложнее отладка, выше риск ошибки в большом пакете.

### 3.2. Консоли запросов

В рабочих базах использовать консоли запросов запрещено — это ухудшает производительность.

### Практическое правило для AI-агента

- предлагать пакетное выполнение только там, где оно действительно полезно;
- не закладывать решения, завязанные на использование консоли запросов в рабочей базе.

---

## 4. Именование объектов и элементов

### 4.1. Изменение типовых объектов

Если меняется архитектура **типового объекта** (новые реквизиты, табличные части и т.п.), в подчинённые объекты добавляется префикс:

- `лвл_`

### 4.2. Добавление новых объектов

Если создаётся **новый объект конфигурации**:

- сам объект — с префиксом `лвл_`;
- подчинённые элементы модели этого нового объекта — **без** префикса `лвл_`.

> Корпоративная особенность: подчинённые элементы нового объекта не наследуют префикс. Это сознательное решение компании level.

### 4.3. Комментарий назначения

Для нового объекта или элемента в комментарии нужно указывать его назначение.

---

## 5. Именование макетов

В имени макета должен быть указан его тип. Допустимые аббревиатуры:

| Аббревиатура | Тип макета |
|---|---|
| `MXL` | табличный документ |
| `TXT` | текстовый документ |
| `BN` | двоичные данные |
| `AD` | ActiveDocument |
| `HTML` | HTML-документ |
| `GeoSh` | географическая схема |
| `GrSh` | графическая схема |
| `СКД` | схема компоновки данных |
| `МОКД` | макет оформления компоновки данных |
| `ExtDll` | внешняя компонента |

### Примеры

- `ПФ_MXL_Заявка`
- `TXT_ШаблонСообщения`
- `ШаблонСтраницыВходаВСистему_HTML`

## 6. Именование процедуры условного оформления

Процедура для изменения условного оформления должна называться:

- `УстановитьУсловноеОформление`

## 7. Оформление вставок в расширениях

Директивы:

- `#Удаление`
- `#КонецУдаления`
- `#Вставка`
- `#КонецВставки`

располагать **по левому краю**.

## 8. Комментарии в коде и метаданных

### 8.1. Общие требования к комментариям

- текст комментария выравнивается по левой границе комментируемого фрагмента;
- между `//` и текстом комментария должен быть пробел.

### 8.2. Комментарий для новых метаданных

Формат:

```bsl
#НомерЗадачиGitLab
// Поясняющий текст: какую цель делает объект конфигурации, который добавлен.
```

### 8.3. Формат комментариев изменений в программном коде

Строго использовать:

```bsl
// ++ #НомерЗадачиGitLab
… изменённый код …
// -- #НомерЗадачиGitLab
```

**Не использовать:**

- фамилии разработчиков;
- даты;
- стрелочки;
- emoji;
- произвольные форматы.

### 8.4. Типовые модули

- запрещено удалять код типового программного модуля;
- изменения в типовом коде оформляются стандартным комментированием.

Пример:

```bsl
// ++ #3465
… новая логика …
// -- #3465
```

### 8.5. Модули собственной разработки

- запрещено оставлять закомментированный код;
- допустимы только комментарии, которые реально объясняют сложную логику, неочевидные конструкции, принцип работы процедуры/запроса.

### 8.6. Комментарии в текстах запросов

- текст запроса не комментируется;
- если нужно объяснить решение, комментарий оставляется не внутри текста, а рядом с объектом `Запрос`.

### 8.7. Документирование процедур и функций

Для **экспортных** процедур и функций заголовочный doc-комментарий обязателен. Для неэкспортных
нетривиальных — рекомендуется. Это не противоречит §8.5: документирование контракта процедуры
является реальным объяснением её назначения (а не «шумом»).

Обязательные секции doc-комментария (перед `Процедура`/`Функция`):

```bsl
// <Назначение процедуры/функции — одна-две строки>
//
// Параметры:
//  <ИмяПараметра> - <Тип> - <Назначение>
//
// Возвращаемое значение:
//  <Тип> - <Назначение>   (только для Функция)
//
Процедура лвл_МояПроцедура(Параметр) Экспорт
```

Правила:

- неуместные секции опускать целиком (нет параметров — секцию «Параметры» не писать; для
  `Процедура` — секцию «Возвращаемое значение» не писать);
- актуально при создании новых и при правке существующих процедур/функций: если doc-комментарий
  отсутствует или устарел (поменялась сигнатура/поведение) — дополнить/актуализировать;
- не дублировать doc-комментарий в комментариях изменений `// ++ #...` (маркер изменений — отдельно);
- сверка формата — стандарт 1С (MCP `v8std`, тема «документирование процедур»; исполнитель
  подтверждает точный id через `v8std_search "документирование процедур"`, не хардкодя id).

## 9. Оформление программных модулей и запросов

### 9.1. Модули

- код разделён по логическим блокам;
- ключевые слова и конструкции выделяются пробелами;
- если область не содержит процедур/функций, её нужно удалить;
- обработчики событий формы/модуля располагаются в том порядке, как в Конфигураторе;
- не допускаются двойные пробелы и лишние переносы строк.

### 9.2. Запросы

- тексты запросов оформлять в виде, который формирует конструктор запросов;
- не менять типовое оформление текста запроса, кроме случаев программной генерации.

---

## 10. Общие принципы доработки типовых механизмов

Главный принцип — минимизировать изменение типового кода.

### 10.1. Макеты

Если нужно изменить типовой макет:

- лучше создать копию и менять её;
- либо вносить изменения в пользовательском режиме, если это применимо.

### 10.2. Формы

Типовые формы документов, справочников и т.д. изменяются **только программным способом**. Не использовать изменение элементов формы через палитру свойств, кроме случаев отсутствия программного доступа. В таком исключении изменения нужно задокументировать комментарием в модуле формы.

### 10.3. Рекомендуемый подход

- в конце `ПриСозданииНаСервере` создавать отдельную процедуру вида `лвл_ДобавитьЭлементыФормы()`;
- по возможности выносить логику в подписки на события, но помнить, что порядок их вызова недетерминирован;
- вместо изменения типового текста запроса — переопределять переменную с текстом запроса или сам объект `Запрос`.

---

## 11. Использование расширений

Расширения допустимы:

- для срочного исправления критичных ошибок;
- для изолированного, независимого функционала.

Расширения **не** допускаются, если:

- в них реализуются доработки основного функционала, не являющиеся исправлением ошибки;
- в них есть механизмы с риском потери данных, нарушения проведения или блокировок.

### Практическое правило для AI-агента

Не предлагать расширение как основной способ реализации обычной бизнес-доработки основной конфигурации.

---

## 12. Обязательное использование стандартных функций и БСП

Общее правило: если есть стандартная функция 1С/БСП, которая решает задачу, нужно использовать её вместо самописной реализации.

### Явно указанные договорённости

Для описания типов использовать:

- `ОбщегоНазначения.ОписаниеТипаЧисло`
- `ОбщегоНазначения.ОписаниеТипаСтрока`
- `ОбщегоНазначения.ОписаниеТипаДата`

Конкатенацию строк делать через `СтрШаблон`.

### Полезные функции, которые рекомендуется применять

**ОбщегоНазначения:**

- `ЗначениеРеквизитаОбъекта`
- `ЗначенияРеквизитовОбъекта`
- `ЗначенияРеквизитовОбъектов`
- `ЗначениеРеквизитаОбъектов`
- `УстановитьЗначениеРеквизита`
- `ТаблицаЗначенийВМассив`
- `УстановитьСвойстваДинамическогоСписка`
- `МенеджерОбъектаПоСсылке`
- `ЗапросВСтрокуXML`

**ОбщегоНазначенияКлиентСервер:**

- `ЕстьРеквизитИлиСвойствоОбъекта`
- `УстановитьСвойствоЭлементаФормы`
- `УстановитьЭлементОтбораДинамическогоСписка`
- `УстановитьПараметрДинамическогоСписка`
- `ЭтоЧисло`
- `НайтиВСписке`
- `ЗначениеВМассиве`
- `СвернутьМассив`
- `УдалитьЗначениеИзМассива`
- `ПустойУникальныйИдентификатор`

**ОбщегоНазначенияКлиент:**

- `СообщитьПользователю`
- `ПредопределенныйЭлемент`
- `ДатаСеанса`

**Прочие:**

- `ОбщегоНазначенияСлужебныйКлиент.ИмяОбъектаМетаданных`
- `СтроковыеФункцииКлиентСервер.СтрокаВЧисло`
- `ПользователиКлиент.ТекущийПользователь`

### Практическое правило для AI-агента

Прежде чем писать свою обёртку/вспомогательную функцию, проверить, нет ли уже подходящего стандартного метода БСП или 1С.

## 13. Проверка заполнения реквизитов

### 13.1. Точка размещения проверки

Все проверки заполнения реквизитов объекта должны быть описаны в:

- `ОбработкаПроверкиЗаполнения` модуля объекта.

### 13.2. Проверки реквизитов формы

Если проверяются данные формы, не относящиеся к объекту, использовать:

- `ОбработкаПроверкиЗаполненияНаСервере` в модуле формы.

### 13.3. Принудительный вызов

Если проверку нужно запускать при записи документа:

- вызывать `ПроверкаЗаполнения()` в `ПередЗаписью()`, после проверки `ОбменДанными.Загрузка`.

### 13.4. Особенности

- если у документа свойство `Проведение = Разрешить`, событие проверки вызывается при проведении;
- если документ не проводится, проверка вызывается при записи;
- если документ проводится из формы и у формы не установлена галка `ПроверятьЗаполнениеАвтоматически`, проверка заполнения не отработает.

### Практическое правило для AI-агента

Не разбрасывать проверки заполнения по случайным обработчикам, если для этого есть стандартные точки расширения.

---

## 14. История данных

Запрещено включать свойство:

- «Обновлять историю данных сразу после записи».

**Причина:**

- создаёт лишние фоновые задания;
- при массовых изменениях перегружает CPU и негативно влияет на весь кластер 1С.

### Практическое правило для AI-агента

Не предлагать и не генерировать решения с включением этого свойства.

---

## 15. Замеры производительности для новых объектов

**Обязательно замерять:**

- открытие форм единичных ссылочных сущностей;
- время записи;
- время проведения.

**Желательно замерять:**

- формы списков, которыми часто пользуются и где часто меняют отборы/сортировки.

### Правило замера

Если замеряется пользовательский процесс:

- замер должен начинаться на клиенте;
- замер должен заканчиваться на клиенте.

**Неправильно:** начинать замер открытия формы только на сервере (например, в `ПриСозданииНаСервере`), потому что тогда не учитывается сеть.

---

## 16. Краткий чек-лист перед выдачей кода

Перед выдачей результата проверить:

- [ ] Для новых объектов/реквизитов соблюдено именование `лвл_`, где требуется.
- [ ] Изменения в коде помечены комментариями формата `// ++ #...` / `// -- #...`, если задача предполагает маркировку изменений.
- [ ] В собственных модулях нет закомментированного кода.
- [ ] Запрос оформлен в стандартном виде, без комментариев внутри текста.
- [ ] Использованы стандартные функции БСП/1С, если они подходят.
- [ ] Проверки заполнения стоят в `ОбработкаПроверкиЗаполнения` / `ОбработкаПроверкиЗаполненияНаСервере`.
- [ ] Не используется обновление истории данных сразу после записи.
- [ ] Для новых объектов предусмотрены замеры производительности.
- [ ] Экспортные процедуры/функции снабжены doc-комментариями (Описание/Параметры/Возвращаемое значение); при правке существующих — актуализированы.
