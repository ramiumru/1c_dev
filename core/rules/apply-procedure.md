# Процедура apply (для 1c-applier)

Детальный алгоритм apply правок в ИБ. Загружается при apply.

## Разрешение базы данных (без авто-выбора)
Запретить автоматический выбор базы, если выполнено любое из условий (→ СТОП, лог `WARN db-ambiguous`):
- база явно не указана в брифе/запросе;
- найдено несколько совпадений (несколько БД проекта);
- конфигурация неоднозначна;
- среда не определена или запрещена (`production`/отсутствует/неизвестна);
- присутствует только признак `default` (без явного id/alias);
- параметры задания не совпадают с конфигурацией.

Алгоритм:
1. Явный `id`/`alias` из брифа → напрямую, но проверить совпадение ровно одной записи.
2. Иначе — проект из брифа: найти запись БД, у которой `aliases` содержит имя проекта ИЛИ
   `configSrc` оканчивается на `projects/<проект>/src`. Несколько совпадений → СТОП.
3. Не найдена / неоднозначна / среда недопустима → СТОП.

## Алгоритм работы
1. **Разрешить целевую базу** (см. выше). Неоднозначна/недопустима → СТОП.
2. **Проверить политику backup.** При `backup_mode: external` — не запускать backup и не
   требовать `backup.md` или хеш backup. Для иных поддерживаемых режимов — подготовить backup
   ДО preflight через `python scripts/safe_backup.py --task <TASK-ID> --db <id>`.
3. **Preflight проверка (dry-run).** Выполнить только проверку:
   `python scripts/safe_apply.py --task <TASK-ID> --db <id> --dry-run`
   Ненулевой exit → СТОП. Прямой вызов `db-load-*`/`db-update` skills
   запрещён правами (frontmatter) — обойти guard нельзя.
4. **Apply (ровно один раз).** При успешной dry-run проверке и наличии пользовательского
   разрешения — выполнить apply:
   `python scripts/safe_apply.py --task <TASK-ID> --db <id>`
   Wrapper сам: находит базу и configSrc, повторно запускает guard (не доверяет прошлому
   dry-run), читает файлы из `06_change_report.md`, проверяет существование и scope,
   вызывает `db-load-xml.ps1` в режиме `Partial`, при успехе вызывает `db-update.ps1`
   для `UpdateDBCfg`.
5. **При ошибке** — остановиться, перечислить выполненные операции. Не повторять apply
   автоматически, не восстанавливать DT. При неясном результате сначала выяснить фактическое
   состояние базы.
6. **После успеха** — проверить результат (сверить фактически изменённые файлы с планом,
   `bsl-check.py` на изменённые `.bsl`). Не вызывать apply второй раз «для проверки».
7. **Успех** → (опц., по брифу) `db-run` открыть Предприятие.

## Ошибки и восстановление
При ошибке:
1. Немедленно остановить выполнение.
2. Не выполнять следующие операции.
3. **Не восстанавливать базу автоматически** (DT-восстановление запрещено).
4. Сформировать отчёт.
5. Перечислить уже выполненные изменения.
6. Указать место ошибки.
7. Оставить восстановление отдельной ручной процедурой (путь к бэкапу в отчёте;
   `db-load-dt -InFile <backup.dt>` запускает пользователь вручную).
