# Процедура apply (для 1c-applier)

Детальный алгоритм apply правок в ИБ. Загружается при apply.

## Разрешение базы данных (без авто-выбора)
Запретить автоматический выбор базы, если выполнено любое из условий (→ СТОП, лог `WARN db-ambiguous`):
- база явно не указана в брифе/запросе;
- найдено несколько совпадений (несколько БД проекта);
- конфигурация неоднозначна;
- среда не определена или запрещена (`production`/отсутствует/неизвестна);
- присутствует только признак `default` (без явного id/alias);
- параметры задания не совпадают с конфигурацией.

Алгоритм:
1. Явный `id`/`alias` из брифа → напрямую, но проверить совпадение ровно одной записи.
2. Иначе — проект из брифа: найти запись БД, у которой `aliases` содержит имя проекта ИЛИ
   `configSrc` оканчивается на `projects/<проект>/src`. Несколько совпадений → СТОП.
3. Не найдена / неоднозначна / среда недопустима → СТОП.

## Repository — source of truth (DB baseline policy)

Repository/source — source of truth; направление доставки — только **repository → БД**.
Никогда не выгружать состояние устаревшей БД поверх repository (`db-dump-xml` — только в
отдельный каталог экспорта/бэкапа); silent БД→src reconciliation запрещён.

Harness не имеет достоверного способа определить divergence БД ↔ repository, поэтому:

1. **DB baseline state: UNKNOWN** (по умолчанию; guard `--baseline unknown`: low/medium → WARN) —
   состояние не считается подтверждённым.
2. **Для `risk: high` apply** UNKNOWN не подтверждён: guard технически блокирует apply
   (FAIL «high-risk apply BLOCKED»; risk — из `03_solution_spec.md`, не из CLI). До apply
   остановиться и потребовать от пользователя явного подтверждения совместимости либо
   выполнения **baseline sync repository → БД** (например, `db-load-xml` Full из repository —
   только явное действие пользователя), затем повторить apply с `--baseline confirmed`
   (safe_apply.py пробрасывает флаг в guard). Лог `WARN baseline-unknown-high-risk`.
3. **Известно, что БД stale/несовместима** → apply BLOCKED (`--baseline stale` → guard FAIL):
   объяснить, что требуется baseline sync repository → БД; repository из БД не менять.
4. **Автоматическая полная загрузка конфигурации без явного действия пользователя запрещена.**
5. **Partial task apply** остаётся существующим механизмом для совместимого baseline
   (load-xml Partial выбранных файлов плана → db-update).
6. `--baseline confirmed` ставится только из явного подтверждения пользователя (прямой режим —
   вопрос; Task-режим — бриф от `1c-do` с зафиксированным подтверждением); само-подтверждение
   запрещено.

## Алгоритм работы
1. **Разрешить целевую базу** (см. выше). Неоднозначна/недопустима → СТОП.
2. **Проверить политику backup.** При `backup_mode: external` — не запускать backup и не
   требовать `backup.md` или хеш backup. Для иных поддерживаемых режимов — подготовить backup
   ДО preflight через `python scripts/safe_backup.py --task <TASK-ID> --db <id>`.
3. **Preflight проверка (dry-run).** Выполнить только проверку:
   `python scripts/safe_apply.py --task <TASK-ID> --db <id> --dry-run`
   Ненулевой exit → СТОП. Прямой вызов `db-load-*`/`db-update` skills
   запрещён правами (frontmatter) — обойти guard нельзя.
4. **Apply (ровно один раз).** При успешной dry-run проверке и наличии пользовательского
   разрешения — выполнить apply:
   `python scripts/safe_apply.py --task <TASK-ID> --db <id>`
   Wrapper сам: находит базу и configSrc, повторно запускает guard (не доверяет прошлому
   dry-run), читает файлы из `06_change_report.md`, проверяет существование и scope,
   вызывает `db-load-xml.ps1` в режиме `Partial`, при успехе вызывает `db-update.ps1`
   для `UpdateDBCfg`.
5. **При ошибке** — остановиться, перечислить выполненные операции. Не повторять apply
   автоматически, не восстанавливать DT. При неясном результате сначала выяснить фактическое
   состояние базы.
6. **После успеха** — проверить результат (сверить фактически изменённые файлы с планом,
   `bsl-check.py` на изменённые `.bsl`). Не вызывать apply второй раз «для проверки».
7. **Успех** → (опц., по брифу) `db-run` открыть Предприятие.

## Ошибки и восстановление
При ошибке:
1. Немедленно остановить выполнение.
2. Не выполнять следующие операции.
3. **Не восстанавливать базу автоматически** (DT-восстановление запрещено).
4. Сформировать отчёт.
5. Перечислить уже выполненные изменения.
6. Указать место ошибки.
7. Оставить восстановление отдельной ручной процедурой (путь к бэкапу в отчёте;
   `db-load-dt -InFile <backup.dt>` запускает пользователь вручную).

## Версия платформы

`safe_apply.py` и `safe_backup.py` выбирают платформу одинаково с обёрткой хранилища:
сначала `databases[].v8path` выбранной базы, затем корневой `v8path`. Выбранный путь
передаётся как `-V8Path` в db-load-xml, db-update и db-dump-dt — один и тот же для загрузки и
обновления. Если путь задан, но недействителен, wrapper завершается ошибкой до запуска
навыка; другая установленная версия автоматически не подставляется. Без обоих значений
навыки ведут себя как раньше.

## Результат этапов и неизвестный исход

- db-load-xml и db-update считают этап неуспешным, если в `/Out` есть строка об отсутствии
  соединения с хранилищем («Соединение с хранилищем конфигурации не установлено» и т.п.) или
  `/DumpResult` не записан/не 0 — даже при exit 0. Неуспешная загрузка не запускает update.
- Каждый этап записывается в `pilot-control/<TASK-ID>/apply-run.json` до запуска и после.
- Незавершённый apply проверяется **первым** — до guard и до lock-refresh, платформа не
  запускается. Блокируют повторную загрузку:
  - этап, запущенный без подтверждённого завершения (таймаут; процесс убит оболочкой);
  - успешная загрузка без подтверждённого обновления: update завершился с ошибкой, не
    запускался или процесс прервался между этапами — основная конфигурация может отличаться
    от конфигурации БД.
  Неуспешная загрузка без следующих этапов не блокирует: состояние ИБ прежнее.
  Повтор автоматически не выполняется. После сверки состояния ИБ человеком (процессы 1cv8;
  основная конфигурация против конфигурации БД) — `--resolve-unknown-outcome "<что проверено>"`;
  решение записывается в журнал (в `--dry-run` не записывается).

## Таймауты и внешняя оболочка

- Лимит этапа — `apply_stage_timeout_seconds` профиля базы (по умолчанию 540 с). Это лимит
  **одного** этапа. Весь вызов `safe_apply` = guard + lock-refresh (у хранилища свой лимит,
  по умолчанию 480 + 60 с) + загрузка + обновление; в общем случае он **не укладывается** в
  лимит одной shell-команды агента (Kilo/OpenCode — не более 600 с).
- `--shell-budget-seconds N` (например, 570 при лимите оболочки 600 с): этап, которому
  остаётся меньше 60 с, не запускается (`exit 4`, в журнале `not_started`), лимит этапа
  урезается до остатка. Lock-refresh этим бюджетом не урезается. Если бюджет кончился после
  загрузки — обновление не запускается, и следующий apply потребует сверки.
- Фактическое поведение при прерывании внешней оболочкой: процесс `safe_apply` убивается без
  записи результата; этап остаётся в журнале `started`; дочерние PowerShell/1cv8 могут
  продолжать работу (на Windows убийство родителя не завершает дочерние процессы, если клиент
  не использует job object с закрытием дерева — для Kilo это не подтверждено); вывод после
  момента прерывания теряется. Следующий `safe_apply` отказывает до сверки.
- Практически: apply с репозиторием запускать из терминала оператора (без лимита) или с
  `--shell-budget-seconds`; фонового режима для apply пока нет.
- Параметры хранилища (`/ConfigurationRepositoryF/N/P`) этапам apply пока не передаются:
  поддержка для `/LoadConfigFromFiles` и `/UpdateDBCfg` на 8.3.27 не подтверждена —
  см. `docs/repository-load-experiment.md`.
