# SDD-реализация (для 1c-developer)

При делегировании через `1c-do` с task-папкой `specs/<TASK-ID>/` — реализация строго по
спецификации, а не «по наитию». SDD-gate — см. инварианты (п.4).

## Что читает разработчик в SDD-режиме
- `specs/<TASK-ID>/03_solution_spec.md` — главный документ-договор (gate, п.4 инвариантов).
- `specs/<TASK-ID>/01_context.md` — контекст и затронутые объекты.
- `specs/<TASK-ID>/05_test_scenarios.md` — критерии приёмки и сценарии проверки.

## Что пишет разработчик в `specs/<TASK-ID>/`
После реализации заполнить `06_change_report.md` по шаблону из `specs/README.md`:
- **«Статус реализации»** — одно из: `выполнено` / `выполнено частично` / `не выполнено
  (блокировано)`. При `выполнено частично` / `не выполнено` — обязательно указать причину в
  «Отклонениях от спецификации».
- **`scope_hash`** — машиночитаемый блок (fenced `yaml`): `scope_hash: <sha256 из spec>`,
  `spec_version: 1`. Берётся из `03_solution_spec.md` (блок status/risk); если там `scope_hash`
  пуст — оставить пустым и отметить в «Отклонениях». `1c-applier` сверяет его при apply.
- «Что сделано» — краткое описание реализации;
- «Изменённые файлы» — **обязательный формат** `<путь> — <КаноническийЗаголовок.Тип.Имя>, <модуль>, <контекст>`.
  Канонический заголовок объекта (Документ.X, Справочник.X, ОбщийМодуль.X, ...) **обязателен** для каждой
  строки — `1c-do` извлекает из него объекты для автообновления summaries (шаг 6.5). Для формы указывать
  родительский объект (Документ.X), не составной (Форма.Документ.X). Без заголовка → summary объекта не
  обновится → устаревание индекса.
  **Правила формата apply-плана:**
  - canonical apply-план находится **только** в разделе `## Изменённые файлы`;
  - каждый файл указывается отдельным элементом Markdown-списка (строка, начинающаяся с `-` или `*`);
  - маски (`*`, `**`, `?`) и каталоги в apply-плане **запрещены** — только конкретные файлы;
  - упоминания путей в остальных разделах («Реализованная логика», «Что проверить вручную» и т.д.)
    являются описательным текстом и **не попадают** в apply-план;
  - `safe_apply.py` и `applier_guard.py` используют один общий парсер `scripts/plan_parser.py`,
    который читает только раздел `## Изменённые файлы` до следующего заголовка `##`.
- «Реализованная логика» — что именно изменено в коде;
- «Отклонения от спецификации» — где реализация отошла от `03_solution_spec.md` и почему («нет» если совпадает);
- «Риски / замечания» — остаточные риски;
- «Что проверить вручную» — конкретные действия для верификации.

## Правила SDD-реализации
- Реализовать в `projects/<источник>/src/**` (по списку «Источники» из брифа) **строго в границах**
  `03_solution_spec.md` (раздел «Границы изменения»): соблюдать не только что МОЖНО менять, но и явный
  **anti-scope** — объекты/модули/поведение вне задачи, которые трогать НЕЛЬЗЯ. Выход за anti-scope
  запрещён. Если правка требует затронуть запрещённое — не додумывать: дополнить «Отклонения от
  спецификации» в `06_change_report.md`, выставить статус `не выполнено (блокировано)` или
  `выполнено частично`, сообщить о возврате к `1c-analyst`.
- Комментарии BSL: `// ++ #<TASK-ID>` … `// -- #<TASK-ID>` (TASK-ID передаёт `1c-do`, разработчик
  его не переопределяет).
- При конфликте spec с фактическим кодом — **не додумывать**: дополнить «Отклонения от
  спецификации» в `06_change_report.md`, сообщить о возврате к `1c-analyst`.
- Не писать `00_request.md`, `01_context.md`, `03_solution_spec.md`, `05_test_scenarios.md` —
  это артефакты `1c-do`/`1c-analyst`. Edit на `specs/**` физически есть, но промптом ограничен
  `06_change_report.md` (и блоком «Отклонения» при конфликте).

## Поведение вне SDD
Если task-папки `specs/<TASK-ID>/` нет (тривиальная/quick-fix правка) — работать как обычно: читать
наработки аналитика из `requirements/`/`summaries`/`{{CONTEXT_DIR}}/projects/<проект>/objects-index.md` и
сразу вносить правку. SDD-правила выше не применяются.
