# SDD-оркестрация (для 1c-do)

Spec-Driven Development — для нетривиальных правок кода. Тривиальные/quick-fix — без SDD.

## TASK-ID
- GitLab-номер из запроса (`#481`) → `TASK-481`.
- Нет номера → сгенерировать `TASK-YYYYMMDD-HHMMSS` по `Current time` системного контекста.
- Тот же TASK-ID разработчик ставит в комментарии BSL: `// ++ #<TASK-ID>` / `// -- #<TASK-ID>`.
  Формат ID определяет только `1c-do`; исполнители его не переопределяют.

## Алгоритм SDD
1. **Классифицировать запрос.** Нетривиальная правка кода → шаг 2. Иначе — обычная маршрутизация.
2. **Определить TASK-ID** (GitLab-номер или `TASK-YYYYMMDD-HHMMSS`).
3. **Создать каркас:** через `write` создать `specs/<TASK-ID>/00_request.md` по шаблону
   `specs/README.md`, заполнить из дословного запроса (секции «Текст запроса», «Тип запроса»,
   «Бизнес-контекст», «Ограничения», «Критерий готовности от пользователя»). При наличии
   релевантного `requirements/<slug>.md` — сослаться в «Бизнес-контексте».
4. **Делегировать `1c-analyst`** (Task, бриф по `task-brief.md`): прочитать `00_request.md` и
   `specs/README.md`, заполнить `01_context.md`, `03_solution_spec.md`, `05_test_scenarios.md`.
   Транспортная Task-ошибка → retry-once; повторная неудача → шаг 7.
5. **Gate — проверка полноты draft-spec.** После возврата аналитика через `glob`/`read` проверить, что
    `03_solution_spec.md` существует и непуст (есть секции «Цель изменения», «Границы изменения»
    (включая anti-scope), «Функциональные требования», «Критерии приёмки») **и содержит
    машиночитаемый блок** `status`/`risk`/`scope_hash` (см. `specs/README.md`).
    Ожидаемый статус на этом шаге — `draft` (аналитик выставляет начальный `status: draft`).
    `approved` НЕ ожидается до human approval (шаг 5.5).
    Опционально — `05_test_scenarios.md`. Неполон/отсутствует →
    повторно делегировать `1c-analyst` **один раз** с указанием конкретного пробела. Повторная
    неудача → лог `WARN sdd-spec-missing`, вернуть пользователю.
5.5. **Human approval flow.** После формирования полноценной draft-spec (шаг 5 пройден):
    a. `1c-do` читает `03_solution_spec.md` и формирует короткое резюме для пользователя:
       цель, scope, risk, предполагаемые изменения, важные ограничения.
    b. Явно спрашивает пользователя через `question` tool: подтверждает ли он спецификацию?
    c. **Только после явного положительного ответа пользователя:**
       - повторно делегировать `1c-analyst` (Task, retry-once): передать факт внешнего approval
         (инструкция: «пользователь подтвердил спецификацию — зафиксируй решение пользователя»);
       - analyst только фиксирует решение пользователя в машиночитаемом блоке:
         ```yaml
         status: approved
         approved_by: user
         approved_at: <ISO 8601 с timezone, напр. 2026-01-01T12:00:00Z>
         ```
       - analyst НЕ принимает решение об approval самостоятельно — он только записывает
         пользовательское решение.
    d. `1c-do` перечитывает spec и убеждается, что: `status: approved`; `approved_by` заполнен;
       `approved_at` timezone-aware (суффикс `Z` для UTC либо смещение `+03:00`).
    e. Только затем запускается developer (шаг 6).
    f. Если пользователь отклонил spec / попросил изменения / не дал однозначного approval —
       статус остаётся `draft`, developer НЕ запускается. Лог `WARN spec-not-approved`.
       Вернуть пользователю причину и предложить уточнить запрос.
6. **Делегировать `1c-developer`** (Task, бриф по `task-brief.md`): прочитать `03_solution_spec.md`
    (обязательно, `status: approved`) + `01_context.md`, `05_test_scenarios.md`; реализовать в
   `projects/<источник>/src/**` строго в границах spec; заполнить `06_change_report.md` (включая
   `scope_hash`); комментарии `// ++ #<TASK-ID>` / `// -- #<TASK-ID>`. Транспортная Task-ошибка →
   retry-once; повторная неудача → шаг 7.
6.4. **Независимый review (для `risk: high` и перед apply).** После шага 6 — через `read`
     `specs/<TASK-ID>/03_solution_spec.md` прочитать машиночитаемый блок: если `risk: high` (или
     эвристика: spec/`06_change_report` содержат high-risk маркеры — проведение, движения регистров,
     транзакции/блокировки, RLS/права, регламентные/фоновые, экспортные процедуры, метаданные,
     интеграционные контракты, структура базы, массовое изменение данных, обмены, финансовые расчёты) —
     делегировать `1c-reviewer` (Task, retry-once): прочитать `03_solution_spec.md` + `06_change_report.md`
     + исходники, сверить scope/регрессии/контракты/тесты, **сформировать полный текст заключения**
     (`verdict` + findings + `spec_version` + `scope_hash` + машиночитаемый yaml-блок) и **вернуть его
     в результате Task**. `1c-reviewer` НЕ сохраняет файл на диск — он возвращает текст.
     **`1c-do` сохраняет полученный текст дословно** в `pilot-control/<TASK-ID>/review.md` через
     `edit`, без изменения verdict, версии, хеша, даты или findings. Затем `1c-do` перечитывает
     файл и сверяет актуальность (spec_version, scope_hash).
     `verdict` ≠ `approved` → лог `WARN review-changes-requested`/`blocked`,
     вернуть задачу `1c-developer`/`1c-analyst`. `verdict: approved` → продолжить.
     Для `risk: low/medium` review опционален, но обязателен перед apply.
6.5. **Проверка статуса и авто-обновление summaries (post-SDD).** После возврата `1c-developer` —
     через `read` прочитать `specs/<TASK-ID>/06_change_report.md`.
     - Статус `не выполнено (блокировано)` / блокирующее отклонение → **НЕ обновлять summaries**,
       лог `WARN sdd-implementation-blocked`, вернуть пользователю.
     - Статус `выполнено` / `выполнено частично` — из «Изменённые файлы» извлечь канонические
       заголовки объектов 1С. **Гибридный роутинг обновления summaries:**
       - все заголовки найдены в индексе → делегировать `1c-tools --objects`;
       - хотя бы один отсутствует (новый объект) → делегировать `1c-tools --scan --objects`;
         лог `WARN auto-scan-triggered`.
     - stdout добавить в ответ блоком «summaries обновлены: <список>».
6.6. **Apply в БД (УСЛОВНО — только если в исходном запросе пользователя было явное намерение
     применить правки в базу; авто-вызова нет).** Выполняется после шага 6.5. Статус — из уже
     прочитанного `06_change_report.md`: `не выполнено`/блокирующее → apply НЕ запускать;
     `выполнено` → пред-обработка на стороне `1c-do` (разрешить базу, делегировать `1c-applier`).
7. **Вернуть ответ** субагента без изменений, добавив префикс `[Делегировано агенту …]`.
