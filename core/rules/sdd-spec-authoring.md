# SDD-спецификация (для 1c-analyst)

При делегировании через `1c-do` с task-папкой `specs/<TASK-ID>/` — подготовить полноценную
спецификацию для разработчика.

## Что читает аналитик в SDD-режиме
- `specs/README.md` — шаблоны артефактов;
- `specs/<TASK-ID>/00_request.md` — исходный запрос и бизнес-контекст (заполняет `1c-do`).

## Что пишет аналитик в `specs/<TASK-ID>/`
Три файла по шаблонам из `specs/README.md`:
1. **`01_context.md`** — затронутые объекты (с префиксами из `.dev.env` / без префикса БСП),
   найденные файлы, текущая логика, связанные механизмы, предположения, неизвестные места
   (с пометкой влияния).
2. **`03_solution_spec.md`** — главный документ-договор с разработчиком. Обязательно заполнить
   секции: «Цель изменения», «Границы изменения» (что можно менять И что менять НЕЛЬЗЯ — явный
   **anti-scope**: объекты/модули/поведение вне задачи, которые трогать запрещено),
   «Функциональные требования» (трассируемые к цели, тестируемые), «Технические требования»
   (техкарта изменения: объект, модуль, контекст выполнения, точка входа, проведение, UI,
   миграции, риск регрессии), «Алгоритм решения» (описание, без BSL), «Затрагиваемые файлы»,
   «Контракты поведения», «Обработка ошибок», «Ограничения совместимости», «Критерии приёмки»,
   «Нефункциональные требования». **В начале файла — машиночитаемый блок** `status`/`risk`/
   `approved_by`/`approved_at`/`spec_version`/`scope_hash` (fenced `yaml`; шаблон —
   `specs/README.md`). Аналитик выставляет начальный `status: draft` и `risk` (low/medium/high по
   классификации в `INSTRUCTIONS.md`); `approved` выставляет внешний субъект (пользователь/
   review-процесс), НЕ сам аналитик для high-risk. **Этот файл — GATE для `1c-developer`: без него
   и без `status: approved` разработка не начинается.**
3. **`05_test_scenarios.md`** — позитивные/негативные/регрессионные/граничные сценарии, что
   проверить в UI и в данных. Каждый сценарий связан с функциональным требованием/критерием приёмки.

## Правила SDD-спецификации
- Не писать BSL-код даже в `03_solution_spec.md` — только описание алгоритма и точки изменения.
- Соблюдать алгоритм шагов 3–5: сначала локальные индексы (`summaries/**`, `{{CONTEXT_DIR}}/projects/<проект>/objects-index.md`,
  `{{CONTEXT_DIR}}/projects/<проект>/analyst-scope.md`), затем точечное чтение `projects/<источник>/src/**` — экономия токенов.
- Использовать маппинг типов → путей при заполнении «Затрагиваемые файлы».
- Выводы — только по прочитанным файлам. Не подтверждённое — в «Предположения» / «Неизвестные
  места» (с пометкой влияния).
- При наличии релевантного `requirements/<slug>.md` — сослаться на него в `01_context.md` и при
  необходимости перенести уточнённые требования в `03_solution_spec.md`.

## Аналитические принципы (best practice)
- **Первопричина, не симптом.** Отделять корневую бизнес-потребность от формулировки запроса.
- **Явные и неявные требования.** Вытаскивать неозвученные ожидания: негативные сценарии,
  граничные случаи, права доступа, влияние на обмены/отчётность.
- **Полнота по жизненному циклу объекта.** Для документа/справочника проверять релевантные этапы.
- **Трассируемость.** Каждое требование связано с «Целью изменения».
- **Тестируемость.** Каждое функциональное требование формулировать проверяемо.
- **Границы решения (anti-scope).** Явно фиксировать, что НЕ входит в изменение.
- **Влияние на систему.** Отмечать риск регрессии: смежные объекты, подписки, обмены, отчёты, контракты.
