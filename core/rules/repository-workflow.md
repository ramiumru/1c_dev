# Хранилище основной конфигурации: первый пилот

Подробная настройка: docs/repository-pilot.md в исходном Harness. В установленном проекте
профиль задаёт пользователь; агенты не редактируют его и не подтверждают binding сами.

1. Пользователь просит изменить, применить и поместить → 1c-do сохраняет эту составную
   цель, определяет db/TASK/scope. Намерение apply не означает намерения commit.
2. Для repository-enabled базы до первой загрузки в ИБ делегировать 1c-repository:
   status/diff и lock существующих объектов с intent prepare. До получения/изменения
   файлов проверить актуальность; не вызывать Revised/update и не затирать source из БД.
3. Разработка, согласование, независимый review и обычные guards остаются прежними.
4. safe_apply для такого профиля требует receipt подготовленного scope и перед загрузкой
   повторяет lock строго тех же объектов. Dry-run этого не делает и сообщает ограничение.
   Полученные неожиданно объекты означают rebase_required, apply блокируется.
5. Только успешные load+update создают evidence для публикации: точный профиль, объекты,
   hash файлов и spec/report/review. Ошибка записи evidence после apply — база уже обновлена,
   не повторять загрузку автоматически. Помещение ожидает отдельной диагностики.
6. Если помещение разрешено пользователем: 1c-repository читает свежий diff выбранных
   объектов и выполняет commit с intent publish. Сформированный комментарий строится из
   смысла задачи. Частная comment_policy_file задаёт обязательный шаблон/поля/проверку.
   Не выдумывать идентификатор корпоративной задачи и не обходить серверную проверку.
7. При commit без изменения отдельный результат «новой версии нет»; при timeout/неясном
   результате — unverified, сначала история/diff. Не повторять ни commit, ни apply вслепую.
8. Отменять только достоверно приобретённые этой задачей захваты, если они больше не нужны.
   Частичный lock не атомарен. Чужие/предшествовавшие задаче свои не освобождать.

Прямой запрос «положи готовую правку» идёт к 1c-repository без повторного apply. Для
несвязанной с SDD операции создай внутренний TASK-ID учёта (не подменяя бизнес-номер задачи),
подготовь scope, проверь diff; --existing-change фиксирует именно такой режим, но не
обходит проверку SDD-задачи. Если источник изменений непонятен/смешан — вернуть вопрос.

Публикация не запускает нового review автоматически, не утверждает функциональную
приёмку и не синхронизирует Git dump. Получение версии и новый top-level объект требуют
отдельного расширения пилота: не обходить запреты ручными параметрами 1cv8.
