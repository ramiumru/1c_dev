# Review checklist (для 1c-reviewer)

Детальные критерии review реализации 1С. Загружается при review.

## Применимость
- 1c-reviewer: полный SDD-процесс ниже, включая разрешённые ему MCP sources.
- 1c-git-reviewer: только критерии «Что проверять» и «Формат замечаний (адресация)»;
  требования scope_hash/SDD-артефактов, YAML verdict и шаг MCP v8std не применяются.
  Для Git-ревью MCP не используется: источники — Git blobs зафиксированной версии.
  Ответ — обычный Markdown без кодового блока вокруг шапки или отчёта.

## Что читает ревьюер в SDD-режиме
- `specs/<TASK-ID>/03_solution_spec.md` — утверждённая спецификация (включая
  машиночитаемый блок `status`/`risk`/`scope_hash` и раздел «Границы изменения»).
- `specs/<TASK-ID>/01_context.md` — контекст и затронутые объекты.
- `specs/<TASK-ID>/05_test_scenarios.md` — критерии приёмки и сценарии.
- `specs/<TASK-ID>/06_change_report.md` — отчёт разработчика (сверить с фактом).
- `projects/<источник>/src/**` — фактические исходники (только чтение).

## Что формирует ревьюер (возвращает через Task, НЕ сохраняет на диск)
Ревьюер **не сохраняет файл на диск**. Он формирует полный текст заключения и возвращает его
в результате Task. `1c-do` сохраняет полученный текст дословно в
`pilot-control/<TASK-ID>/review.md`.

Полный текст заключения включает машиночитаемый yaml-блок:

```yaml
verdict: approved | changes_requested | blocked
reviewed_by: 1c-reviewer
reviewed_at: <ISO 8601 с timezone, напр. 2026-01-01T12:00:00Z>
spec_version: 1
scope_hash: <hash из spec или пересчитанный>
```
плюс секции: «Сверка со спецификацией», «Scope», «Регрессии и риски», «Запросы и
производительность», «Права и RLS», «Интеграционные контракты», «06_change_report»,
«Тесты», «Findings» (severity: info/warning/critical + описание).

## Критерии verdict
- `approved` — реализация соответствует spec, нет выхода за scope, нет `critical`
  findings, тесты/`bsl-check`/`*-validate` пройдены (или риски приняты). Обязателен для
  `risk: high` и перед передачей в `1c-applier`.
- `changes_requested` — есть `warning` findings, требующие доработки, но без блокировки.
- `blocked` — выход за scope, `critical` findings, несоответствие spec, провал тестов,
  нарушение контрактов/прав. Разработка должна вернуться к `1c-developer`/`1c-analyst`.

## Что проверять
- **scope_hash (обязательно):** пересчитать хеш самостоятельно командой
  `python scripts/scope_hash.py --spec specs/<TASK-ID>/03_solution_spec.md`
  и сверить с значением в yaml-блоке spec, `06_change_report.md` и `review.md`.
  Несовпадение → `blocked` (scope изменён после approval). Перенос хеша из spec без
  независимого пересчёта недопустим. Изменение scope аннулирует прежнее согласование.
- **Соответствие spec:** реализация решает заявленную цель в границах «Функциональных
  требований» и «Критериев приёмки».
- **Scope:** незаявленные изменения (объекты/модули/поведение вне «Границ изменения» и
  anti-scope) → `blocked`.
- **Строки и локализация:** проверить изменённый код по
  `{{CONTEXT_DIR}}/rules/bsl-strings.md`: `СтрШаблон` для составных текстов, `НСтр`
  для пользовательских фраз, русский по умолчанию; технические строки не локализовать.
- **Регрессии:** смежные объекты, подписки на события, обмены, отчёты, проведение,
  движения регистров.
- **Транзакции и блокировки:** `НачатьТранзакцию`/`Зафиксировать`/`Отменить`, блокировки
  данных, обработка ошибок, тупики.
- **Запросы и производительность:** запросы вместо циклов, индексы, объёмы, N+1.
- **Публичный интерфейс и повторное использование:** проверить новые `Экспорт`
  (внешний потребитель/обязательный контракт), внутренние помощники и повтор алгоритмов
  между объектами по `{{CONTEXT_DIR}}/rules/bsl-design-and-queries.md`. Не требовать
  удаления существующего API по одному лишь отсутствию найденных прямых вызовов.
  Для общих фрагментов оценить общий метод, контекст и scope; указать конкретные копии.
- **Табличные параметры запроса:** таблица значений сначала загружается во временную
  таблицу, обработка и соединения идут следующим запросом. Проверить типы колонок
  и менеджер при разделённых запросах; не путать со скалярами/`В (&Список)`. Такой
  дефект нельзя считать проверенным одним структурным `bsl-check`.
- **Права и RLS:** `РАЗРЕШЕННЫЕ`, RLS-шаблоны, роли; влияние на права.
- **Интеграционные контракты:** обратная совместимость публичных экспортных процедур,
  точки входа, XDTO/обмены.
- **`06_change_report`:** список изменённых файлов и описанная логика соответствуют
  фактическим изменениям исходников.
- **Тесты:** результаты доступных безопасных проверок — `python scripts/bsl-check.py`,
  `*-validate` (структура XML), сценарии из `05_test_scenarios.md`.

## Формат замечаний (адресация) — обязателен для каждого finding/замечания

Каждое замечание/finding должно содержать точный адрес проблемы, чтобы её можно было
найти без дополнительных вопросов. Поля обязательны; если поле неприменимо — явно указать
причину. Запрещены замечания вида «только объект + SHA коммита» без пути файла и строки —
такое замечание считается неполным.

Структура:
- **Конфигуратор:** — полный путь объекта как в конфигураторе 1С, без сокращений.
  Примеры: «Обработки → <ИмяОбработки> → Модуль менеджера»,
  «Отчёты → <имя> → Формы → <имя формы> → Модуль формы». Для макета — полный путь до
  макета и конкретный элемент (область/параметр), если его можно определить.
- **Файл:** — путь к файлу относительно корня репозитория (например,
  `projects/<источник>/src/DataProcessors/<имя>/Ext/ManagerModule.bsl`). Указывать
  фактический путь целиком; `Module.bsl` без владельца и «там же» недостаточны.
  Для формы полный адрес: `Документ.<Имя>.Форма.<ИмяФормы>.Модуль`.
- **Место:** — имя процедуры/функции (если замечание относится к её коду) и точный
  номер строки или небольшой диапазон. Версия, к которой относится адрес:
  - **1c-git-reviewer** (работает по Git diff): добавленный/изменённый код — новая
    версия (SHA коммита); удалённый код — старая версия (версия родителя коммита, т.е.
    `<SHA>~1`). SHA **дополняет** адрес, но не заменяет путь и строку.
  - **1c-reviewer** (работает по рабочему дереву): текущая редакция файла в
    `projects/<источник>/src/**`.
- **Замечание:** — краткое объяснение проблемы и её последствия.

Пример (обычный текст ответа, не кодовый блок):

[P2] Удалён вызов процедуры расчёта
Конфигуратор: Обработки → <ИмяОбработки> → Модуль менеджера
Файл: projects/finance/src/DataProcessors/<ИмяОбработки>/Ext/ManagerModule.bsl
Место: Процедура РассчитатьСмету, строка 123 старой версии (родитель <SHA>~1)
Замечание: удалён вызов <…>; это может привести к <…>.

Правила:
- **Не выдумывать** пути и номера строк. Определять их по исходникам и Git diff.
- Если точное место установить невозможно — явно указать, что не удалось определить, и
  почему (например, «изменение разнесено по нескольким процедурам без однозначной
  привязки к строке»).
- Если проблема затрагивает и модуль, и макет — приводить **отдельный адрес** для
  каждого места.

## Алгоритм работы
1. Прочитать `03_solution_spec.md` (блок status/risk + «Границы изменения»),
   `01_context.md`, `05_test_scenarios.md`, `06_change_report.md`.
2. Для каждого изменённого файла из `06_change_report` — `read`/`grep` фактического
   исходника; сверить с описанием отчёта и spec.
3. Запустить `python scripts/bsl-check.py <изменённые .bsl>`; для XML — `*-validate`.
4. При конструкциях-триггерах (транзакции, РАЗРЕШЕННЫЕ, обмены, регламентные, XDTO,
   подписки, экспортные процедуры) — сверка через MCP `v8std` (при доступности, иначе
   fallback `AGENTS.md`/level).
5. Сформировать полный текст заключения (verdict + Findings + yaml-блок с `spec_version`
   и `scope_hash`). Вычислить/сверить `scope_hash` командой
   `python scripts/scope_hash.py --spec specs/<TASK-ID>/03_solution_spec.md`.
6. **Вернуть полный текст заключения в результате Task** — не сохранять на диск.
   `1c-do` сохраняет полученный текст дословно в `pilot-control/<TASK-ID>/review.md`.
   Ревьюер не записывает файлы через `edit`.
7. Ответ — краткий verdict + указание, что полный текст возвращён в результате Task.
