# Windows: Python существует, но агент его не запускает

Установка Python и доступность команды в процессе клиента — разные факты. Store/PATH
ошибка не доказывает отсутствие установленного интерпретатора, а запрет инструмента
вообще не проверяет интерпретатор. Не переустанавливайте Python и не снимайте защиту
по одному пересказу модели.

## Собрать факты без Python и административных прав

Откройте обычный PowerShell под тем же пользователем. В корне установленного проекта:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/check-python.ps1
```

В source checkout путь — `core/scripts/check-python.ps1`. Если известен реальный путь:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/check-python.ps1 -PythonPath "C:\Users\User\AppData\Local\Programs\Python\Python313\python.exe"
```

Пример пути не означает, что Python обязательно находится именно там. Скрипт проверяет
команды текущего процесса, возвращает реальный interpreter/version при запуске и
различает отсутствие команды в PATH, непроверенный WindowsApps alias и ошибку запуска.
Он не меняет PATH/config/registry, не устанавливает Python/пакеты и отключает
install-on-launch в окружении проверяемого дочернего процесса. Store alias не запускается.
Он не читает креды и не выводит полный PATH или произвольный stderr программ.

Вывод относится к этому PowerShell, а не ко всем процессам машины. VS Code/Kilo могут
сохранять старое окружение: после изменения PATH нужен полный перезапуск клиента.
При рабочем интерпретаторе с явным путём, но нерабочем `python`, сначала исправляется
выбор команды/окружение пользователя, а не выполняется повторная установка от admin.

## Запуск Harness

Для уже установленного runtime на Windows поддержан эквивалент:

```text
python scripts/git_readonly.py --repo projects/example/src status --short
py -3 scripts/git_readonly.py --repo projects/example/src status --short
```

В Kilo/OpenWork `py -3` разрешён только для тех же scripts и аргументов, что и python,
в роли, которая уже имела такое право. Arbitrary `py -c`, `py -m`, установка пакетов,
raw Git и изменения глобальных настроек этим не разрешены. Claude/Codex используют
обычные ограничения окружения; новые универсальные права им не выдаются.

Сначала подтвердите установленный runtime диагностикой. Если py отсутствует или тоже
недоступен, это не решение; используйте факты о фактическом PATH/клиенте и профиль
поддержки компании. Не разрешайте произвольные абсолютные пути/весь bash ради запуска.
Для нового Python Install Manager отдельно учитывайте install-on-launch: Harness не
предлагает установку как автоматический fallback.

## Разобрать отказ прав

Сохраните точный вызов shell из истории инструмента и исходный отказ. Важно различать:
`python scripts/...`, `python.exe ...`, полный путь и `cd ... && python ...`. Это могут
быть разные проверяемые команды. Не добавляйте cd/проверку PATH к вызову wrapper из
корня установленного проекта; путь Git передаётся через --repo.

Проверьте фактически загруженные agent files, конфиги проекта/пользователя и настройки
инструмента, не выводя секретов. Строка `source: global` в сообщении не устанавливает
путь файла и сама по себе не доказывает, что агентский allow не работает.
Правила Kilo проверяются в порядке конфигурации; последнее совпавшее правило побеждает.
Каждая команда составного shell-вызова проверяется отдельно. Это не основание удалять
все deny или добавлять несуществующее поле `source: agent` во frontmatter.

После изменения только подтверждённого конфликтующего правила нужен новый чат/перезапуск
клиента и реальный вызов разрешённого wrapper. Обновление Harness не исправляет намеренный
внешний запрет организации. До успешного вызова на пострадавшем ноутбуке incident не закрыт.
