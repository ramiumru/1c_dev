# Пилот: основная конфигурация и хранилище 1С

В public Harness добавлены skill 1c-repository-manage и исполнитель 1c-repository.
Координация — через 1c-do. Возможны составная задача с apply и самостоятельное
помещение готового изменения. На рабочем dev-хранилище автоматически ничего не
выполняется: профиль и первый тест настраивает пользователь.

## Границы первой версии

Поддержаны status/history/diff/lock/commit/unlock для существующих объектов основной
конфигурации. Нет force, update/-Revised, bind/unbind, новых объектов, захвата корня,
IncludeChildObjects и расширений. Автоматический scope вложенных подсистем не включён.
Операция помещения публикует объект целиком, не только выбранные строки BSL.
Нельзя использовать создание закомментированного кода там, где стандарт запрещает его:
для теста подойдёт осмысленный обычный комментарий в согласованном существующем модуле.

Status получает историю последней версии и проверяет доступ к хранилищу. Это **не
автоматическая проверка привязки ИБ**. В первом пилоте пользователь открывает нужную ИБ
в Конфигураторе, проверяет адрес подключения и текущую учётную запись хранилища и только
после этого ставит binding_confirmed. Обёртка честно маркирует evidence как user-confirmed.
Не использовать update для «пробы подключения». Подключение/отключение выполняются вне skill.

Для общего dev-хранилища заранее выберите один существующий объект и согласуйте тест
с коллегами. Конфликт не обходится force. Частичный захват не откатывается автоматически.
После неопределённого commit сначала история/diff: он мог выполниться, даже если клиент
не получил результат. Повторный apply для исправления публикации не выполняется.

## Профиль

В существующую запись базы `.v8-project.json` добавьте **вручную** секцию:

```json
"repository": {
  "enabled": true,
  "environment": "dev",
  "path": "tcp://repository-server/dev",
  "username_env": "ONEC_REPOSITORY_USER",
  "password_mode": "env",
  "password_env": "ONEC_REPOSITORY_PASSWORD",
  "allow_write": false,
  "binding_confirmed": false
}
```

Внешняя запись базы должна иметь environment local/test/staging (не production),
точный type и path либо server/ref; платформа задаётся v8path. Выбор базы — только
по однозначному db_id. У репозитория собственный environment: dev/test/staging для
мутаций; любое другое значение блокирует мутации, включая prod/production.
allow_write включается пользователем отдельно от allow_apply. Разрешение публикации
не даёт права загрузки в ИБ, и наоборот. Без repository.enabled прежний apply-процесс
не меняется. .v8-project.json и реальные настройки/credentials не коммитить.

Пароль ИБ и пароль хранилища — разные env-переменные. В конфиге только их имена;
plaintext-поля отвергаются. Чтение идёт в фактическом Process environment, не из .dev.env.
После настройки Windows User env полностью перезапустите клиент/VS Code, чтобы новый
процесс унаследовал значения. Не просите модель прочитать значения и не отправляйте их
в чат. Пароль передаётся 1cv8.exe его штатным аргументом внутри запускающего процесса;
env не отменяет видимость внутренних process arguments привилегированным средствам ОС.

Начните со status/diff при allow_write=false. После проверки выбранной ИБ/хранилища,
scope и владельцев захватов включите allow_write и binding_confirmed для пилота.

## Комментарий: public и private

Если пользователь дал текст, передаётся --comment. Иначе агент читает реальную правку,
составляет краткую --summary и получает нейтральный комментарий `TASK-ID: смысл правки`.
Обёртка сама смысл кода не выдумывает. Для корпоративного формата задаётся локальный
`repository.comment_policy_file` и `repository.comment_policy_required: true`, например `private/repository-comment.json`:

```json
{
  "template": "#{task_ref}: {summary}",
  "required_fields": ["task_ref", "summary"],
  "validation_regex": "#[0-9]+: .+"
}
```

Это лишь пример схемы, не утверждение вашего настоящего формата. Реальный файл и
шаблон поставляются корпоративным overlay. Доступные поля: task_id (внутренний TASK-ID
учёта), task_ref (реальный номер бизнес-задачи, --task-ref), summary, objects. Номер
бизнес-задачи не генерировать и не подменять внутренним TASK-ID. Если поле обязательно
и неизвестно — запросить его. Не подставлять вымышленные значения.

При comment_policy_required отсутствие пути к политике тоже блокирует помещение.
При настроенной политике отсутствие/неполнота файла или неправильный комментарий
блокируют платформу. Готовый --comment тоже проходит validation_regex; без него готовый
корпоративный комментарий не принимается. Серверный перехват/веб-сервис 1С остаётся
окончательным контролем; отказ не обходится и отдельный вызов веб-сервиса не дублируется.

## Последовательность

1. Для общей SDD-задачи определите точные существующие объекты и TASK-ID. 1c-repository
   выполняет status/diff, затем lock с --intent prepare до первой загрузки в ИБ.
2. Разработчик/reviewer работают как прежде. Апликер проверяет свои существующие gates.
   Для repository-enabled базы safe_apply требует подготовленный scope и непосредственно
   перед загрузкой повторяет lock выбранных объектов. Отказ/получение неожиданных версий
   блокирует загрузку: исходники не перезаписываются из базы.
3. Только успешные load+update формируют apply evidence с хешами исходников/spec/report/review.
   Если evidence записать не удалось, база уже обновлена: не повторять загрузку вслепую.
4. После чтения свежего diff и при разрешённом пользователем помещении — commit с
   --intent publish. Source/spec/review после apply должны быть неизменны. Внешние изменения
   в самой базе нельзя доказать отсутствующими одними файловыми хешами: агент обязан
   проверить diff и не публиковать смешанные/непонятные правки.
5. Новая версия, отсутствие новой версии, ошибка и неизвестный результат — разные исходы.
   Номер версии подтверждается чтением истории; latest-version сам по себе не доказывает,
   что эта версия создана именно нашим вызовом при параллельной работе коллег.
6. Если в scope есть ранее свои захваты, commit запрашивает KeepLocked: их не освобождаем
   как побочный эффект публикации. Захваты, приобретённые только этой задачей, при обычном
   commit могут освободиться штатно. Флаг и оставшиеся захваты отражаются в receipt.
   Unlock допускается только для достоверно приобретённых этой задачей захватов, которые
   ещё не были освобождены/помещены. Ранее свои и чужие захваты не присваиваются задаче.

Для отдельного запроса «положи этот объект» без SDD/apply в Harness — новый внутренний
TASK-ID, точный scope, status/diff, prepare, затем commit --existing-change. Это явная
публикация уже существующего изменения, а не утверждение, что Harness его применил или
провёл независимый review. Если SDD spec этой задачи существует, флаг не обходит apply evidence.

```powershell
python scripts/safe_repository.py --db dev --operation status
python scripts/safe_repository.py --db dev --operation diff --objects ОбщийМодуль.МойМодуль
python scripts/safe_repository.py --db dev --operation lock --objects ОбщийМодуль.МойМодуль --task TASK-PILOT --intent prepare
python scripts/safe_repository.py --db dev --operation commit --objects ОбщийМодуль.МойМодуль --task TASK-PILOT --intent publish --existing-change --summary "уточнено пояснение метода" --task-ref 123456
```

Сначала добавьте --dry-run к изменяющей команде для проверки профиля/политики/evidence.
Он ничего не запускает и не обещает готовность соединения, захватов или платформенной
проверки. Actual commit после проверки должен быть явно разрешён пользователем.

Журналы: pilot-control/TASK-ID/repository/<run>/receipt.json, result.json, platform.log,
runner.log, objects.xml, comment.txt/report.txt по операции. Они сохраняются при частичном
отказе; credential-значения маскируются. Receipts — факты вызовов обёртки, не доказательство
подлинности против локального администратора с правом переписать весь проект.

Установку/обновление на Windows запускайте от своего обычного интерактивного пользователя.
Файлы `.agents`/`.codex` не должны принадлежать техническому пользователю CodexSandboxOffline:
иначе после установки возможен отказ доступа ещё до запуска операций 1С.

Для Windows sandbox действует обычная поддерживаемая эскалация. Если 1С не может запуститься
под sandbox-пользователем, не выдавать это за ошибку хранилища и не отключать sandbox;
сохранить диагностику и ту же guard-обёртку для штатного запуска пользователем.

## Проверка перед общим dev-хранилищем

Офлайн: негативные профили, секреты, политика, частичный захват, потерянный ответ,
невозможность освободить прежний захват, невозможность обойти apply evidence, изменения
source/review, неизменённый объект без новой версии и нулевой exit без подтверждения.
Windows fake-platform проверяет настоящий PowerShell-исполнитель без живой 1С.
Затем на рабочей машине — отдельный согласованный объект: status/diff → lock → небольшое
изменение → проверки/apply → commit с реальным корпоративным форматом → история и захваты.
Если реальный журнал отличается от fixtures, состояние unverified: сначала диагностика,
а не ослабление guard ради прохождения.
