# Мастер настройки хранилища

В установленном workspace попросите **1c-do**: «Настрой хранилище для finance-dev.
Сначала покажи план. Пароль в чат не передаю». Мастер работает с существующей базой
в `.v8-project.json`; создание базы и изменение её подключения в этот маршрут не входят.

1c-do опрашивает пользователя, 1c-repository запускает специальную утилиту.
Новая роль не нужна. Прямое редактирование JSON агентами остаётся запрещённым.
При составной задаче настройка проверяется до реализации, а не перед самым apply.

## Порядок

Из корня установленного проекта (подтверждённый `py -3` можно использовать вместо `python`):

```powershell
python scripts/repository_setup.py check --db finance-dev
```

`needs_setup` означает неполноту профиля. `configured` означает корректность локальных
параметров; это не проверка связи с 1С. `credential_presence` сообщает только наличие
значений в окружении текущего процесса, без их вывода.

Подготовьте план с настоящими значениями вместо примеров:

```powershell
python scripts/repository_setup.py plan --db finance-dev --v8path "C:\Program Files\1cv8\8.3.xx.xxxx\bin\1cv8.exe" --repository-path "tcp://repository-server/dev" --repository-environment dev --username-env ONEC_REPOSITORY_USER --password-env ONEC_REPOSITORY_PASSWORD --comment-policy-file ".kilo/context/projects/_corporate/repository-comment.json"
```

Адрес хранилища может быть `tcp://...`, `http://...`, `https://...` либо абсолютным
файловым/сетевым путём. HTTP(S)-адрес веб-публикации передаётся платформе целиком:
путь публикации, порт, регистр, экранирование и завершающий `/` не переписываются.
Логин/пароль внутри URL запрещены; используются имена env. Мастер и рабочая
обёртка применяют одну проверку URI. Проверка формата не доказывает доступность
публикации или привязку базы; это проверяется отдельно.

Для OpenWork/Claude/Codex путь политики берётся из их фактического установленного
контекста. В публичном pet-проекте флаг политики необязателен. В корпоративном
проекте агент обязан взять корпоративную политику из контекста; неизвестный путь
нужно уточнить. Флаг включает `comment_policy_required`; существующая политика
сохраняется. Мастер не предоставляет команды отключения обязательной политики.

Новая настройка по умолчанию сохраняется с `enabled=true`, `allow_write=false`,
`binding_confirmed=false`. Имеющиеся параметры сохраняются; при смене адреса/контура
хранилища прежние разрешение записи и подтверждение привязки сбрасываются.

Покажите пользователю `changes`. После его одобрения выполните `save` с **теми же
параметрами** и `--approve <approval_token>` из результата plan. Токен связывает план
с точными исходным профилем, предлагаемым файлом и содержимым политики. Токен не
является самостоятельным доказательством согласия человека: это контролирует агент.
Изменение профиля/плана/политики требует нового согласования.

Сохранение создаёт побайтовую резервную копию `.v8-project.json.<id>.backup`, затем
атомарно заменяет профиль. Другие базы, неизвестные поля и `allow_apply` сохраняются.
Для записываемых мастером файлов используется блокировка. После аварийного завершения
оставшийся `.v8-project.json.setup.lock` удаляется вручную только после проверки, что
другой мастер не работает. Не коммитьте профиль, backup, временные файлы и lock.

## Окно ввода логина и пароля

Пользователю не нужно запускать PowerShell и вводить команды. В Windows 1c-do
включает в показываемый план `--credential-source windows-user-env`. После одобрения
и сохранения плана 1c-repository вызывает `repository_setup.py credentials --db <id>`.
Открывается отдельное Windows-окно: выбранная база и адрес, текущий пользователь
Windows, логин, скрытое поле пароля, кнопки «Сохранить» / «Отмена».

PowerShell остаётся внутренним механизмом запуска окна. Значения не передаются
в параметры команд, чат, stdout, профиль или файлы статуса. Отмена не сохраняет
credentials. В User environment хранятся значения только двух выбранных переменных;
это тот же способ хранения, что использовался ранее, а не защищённый сейф паролей.

Action возвращает request_id и `dialog_requested` — это ещё не доказательство
появления окна или сохранения. Затем агент проверяет `credentials-status --db <id>
--request-id <id>`. Возможны pending/saved/cancelled/error/unverified. После 10 минут
без результата состояние unverified: не открывать второй диалог и не продолжать
операции автоматически. Если окно не появилось (например, недоступен интерактивный
рабочий стол), сообщить о проблеме запуска интерфейса. Не заменять её требованием
ввести пароль в чат или выполнить команды вручную.

В режиме windows-user-env каждый запуск обёртки заново читает из Windows User
только выбранные переменные хранилища. Значения передаются дочернему процессу 1С
через его окружение. Старое Process значение не используется как fallback,
если User значение отсутствует. `%` в пароле не раскрывается как ссылка на env.
**Перезапуск VS Code после ввода этих данных больше не требуется.** Нужны тот же
Windows-пользователь и доступный интерактивный рабочий стол для окна.

Существующий `credential_source: process-env` (также значение по умолчанию) сохраняет
прежний контракт: чтение окружения процесса. Его смена на windows-user-env выполняется
обычным plan → одобрение → save, без прямой правки профиля агентом. Настройки credentials
самой ИБ и других баз не меняются.

## Проверка перед работой

После saved с credentials_available выполнить check и read-only status/diff через
safe_repository. Сохранение не проверяет соединение с 1С. Только пользователь
подтверждает в Конфигураторе привязку именно этой ИБ к этому хранилищу. Разрешение
записи включается отдельным согласованным планом `--allow-write yes`; окно credentials
не выполняет lock/apply/commit и не меняет разрешения.

Исходная задача продолжается с сохранённого состояния. Если prepare изменил файлы,
реализация и ревью проверяются снова в необходимом объёме. Повторный apply для
исправления настройки или публикации не выполняется.
