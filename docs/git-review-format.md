## Принципы оформления

- Статус должен читаться первым; его смысл всегда выражен словами, не только значком.
- Один дефект — один заголовок. Между абзацами и перед списками нужны пустые строки.
- Адреса — самостоятельный список; не сливать объект, путь и строки с объяснением.
- Имена процедур, пути, SHA и короткие выражения — inline-код. Несколько строк кода —
  отдельный code block с языком bsl/xml; весь отчёт никогда не помещается в один блок.
- Подсветку выбирает клиент и тема. Если bsl не поддержан конкретной сборкой, блок
  остаётся читаемым без цветов. HTML/ANSI и изменение настроек клиента не требуются.
- Рекомендации, вопросы и ограничения не смешиваются с доказанными дефектами.
  Не скрывать существенный пробел за зелёным статусом.
- Краткий scope не превращается в перечень всех строк и успешных проверок. Нет нужды
  повторять итог в конце или писать «формирую отчёт» перед готовым результатом.

Основа: [Google Engineering Practices — review comments](https://google.github.io/eng-practices/review/reviewer/comments.html),
[GitHub — code blocks и язык подсветки](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-and-highlighting-code-blocks).
Это адаптация для Harness, а не требование использовать полный сторонний стандарт.
